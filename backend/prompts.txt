IMPLEMENT LLM CALLS IN THE BUG DETECTOR, USING THE SAME OMNIROUTE SETUP AS RCA

Goal: Collector 4 (LLM reviewer) and the llm verification step in the bug detector must call the LLM through OmniRoute, using the same client, configuration, and environment variables the RCA already uses. Do not add RCA to orchestrator.py. Do not print or commit secret values.

RULES
- Do not read anything under old_orchestrator or tests\answer_keys.
- Do not print the values of any environment variable. Report variable names only.
- Do not commit or modify .env. Confirm .env is in .gitignore; if it is not, report that and stop.
- Do not change RCA behavior. If you move shared code, RCA must keep working with no change in its output.
- Do not add RCA to orchestrator.py.

STEP 0: STATE
Run `git status --short` and `git log --oneline -3` and quote them. Start only if the working tree is clean. If it is not, list the changed files and stop.

STEP 1: STUDY HOW RCA CALLS OMNIROUTE (read only, no edits)
1.1 Find every file that calls OmniRoute. Search for "omniroute", "OMNIROUTE", "base_url", "api_key", "chat.completions", "messages.create", and "requests.post" across the backend, excluding old_orchestrator. Quote each match with file and line.
1.2 For the RCA call path, report:
   - The client module and class or function that makes the request.
   - The environment variable names it reads (names only). Check .env with a command that prints names only, for example: `Get-Content .env | ForEach-Object { ($_ -split '=')[0] }`. Do not print values.
   - How the model name is chosen (config file, env var, or hardcoded). Quote the line.
   - Request shape: endpoint, headers, body fields such as model, max tokens, temperature, and messages.
   - Response parsing: which field holds the text.
   - Timeout, retry, and error handling.
   - Any caching or rate limiting.
1.3 Report whether the RCA client can be imported from the bug detector without side effects (no orchestrator import, no global state that starts a run).
1.4 Report the LLM_DISABLED variable: where it is read, where it is set, and everything that sets it. Quote each line. Note that the earlier run set it because of --stop-after. The bug detector runs before the stop point, so that is a bug to fix in Step 3.

STEP 2: SHARED CLIENT
2.1 If the RCA client is in a module the bug detector can import, import it and do not copy it.
2.2 If it is only inside the RCA code, move the client into backend\llm\omniroute.py with the same function signature and behavior. Update the RCA to import it. Quote the diff for RCA. The RCA's behavior must not change.
2.3 The client must expose one function, for example call_omniroute(prompt, max_tokens, temperature) -> str, that raises a typed error on failure. Do not put any run state inside it.

STEP 3: COLLECTOR 4 (LLM REVIEWER)
3.1 Function selection: select every function from index.json that contains an if, a call, or a return. Include methods. Quote the total selected count.
3.2 Prompt: build one prompt per function containing:
   - Qualified name, signature, and docstring.
   - The function body with line numbers, taken from the file using line_start and line_end.
   - "Calls" and "Called by" from graph.json, using qualified names. Show "none" when empty.
   - The required JSON output schema: {"category": string, "line_start": int, "line_end": int, "reason": string} or {"no_bugs": true}.
   - The instruction: report only defects that are visible in the code. Do not report style issues.
3.3 Cache: key the cache on sha256(model + prompt). Store responses in runs\cache\llm\. On a cache hit, do not call the API. Count hits.
3.4 Call: send each prompt sequentially through the shared client. Set a timeout and retry up to 2 times on network or 5xx errors, with exponential backoff. Do not retry on 4xx or parse failures.
3.5 Save each raw response to the run directory as llm_review_<n>.txt, with the prompt followed by the response. One file per function, numbered in selection order.
3.6 Validation, in this order:
   a. Parse the response as JSON. If parsing fails, try to extract the first JSON object from the text. Count a rejected response if that also fails.
   b. If the object is {"no_bugs": true}, count it as valid with no candidate.
   c. Otherwise require category (non-empty string), line_start and line_end (integers), and reason (non-empty string).
   d. Require line_start <= line_end, and both within the function's line span from index.json. Reject otherwise.
3.7 Valid bug responses become llm candidates with source "llm", the function's qualified name as symbol, the returned line span, the category, and the reason as description. Keep the raw response in candidate.raw.
3.8 Failure isolation: an error on one function is logged and counted, and the loop continues.
3.9 Kill switch: replace the LLM_DISABLED behavior with a dedicated flag, for example --llm off, that defaults to on. --stop-after must not disable the LLM collector. Report the old and new flag definitions.

Write them from the collector's own counters, not from the number of files written.

STEP 6: FULL COLLECTOR RUN
6.1 Run the full pipeline once through the orchestrator on tests\fixtures\api_server.
6.2 Quote the new run_id and the status counters from status.json.
6.3 Check that llm_functions_selected equals the number of llm_review files written plus cache hits. Quote both numbers.

STEP 7: VERIFY LLM CANDIDATES (only after Step 5 and Step 6 pass)
7.1 For each llm candidate, ask the LLM for one pytest test that exercises the suspect function with inputs that should expose the bug. Use the same client and the same cache.
7.2 Write the test to runs\<run_id>\repro\<candidate_id>\test_repro.py. Do not write into the repo.
7.3 Run it in a subprocess with a 60-second timeout.
7.4 Mark confirmed only if the test fails with an assertion or an exception raised from the suspect code. Mark unconfirmed otherwise, with the reason.
7.5 Quote the verification result for the _validate_user candidate.
